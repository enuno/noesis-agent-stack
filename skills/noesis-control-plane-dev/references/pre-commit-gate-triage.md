# Pre-commit gate triage

Use when a pre-commit hook, validator, or test gate refuses a commit. The
always-on rules live in the parent SKILL.md under "Attribute a blocking gate
failure before acting on it" and "When a validator reports the same error once
per file"; this file is the executable recipe.

## Step 1 — read the gate, don't pattern-match its errors

A gate's message describes what it checked, not what is broken. Identify:

- which gate failed (hook stage, script, rule id)
- which paths it flagged
- whether it exits on the first failure or reports all

Then decide: is this gate even about your change? A gate that validates a
different subsystem can fail on a commit that never touched it.

## Step 2 — attribute: pre-existing or introduced

Never infer the cause from the fact that the commit was blocked. Prove it:

```bash
# Preserve the work, then reproduce on a clean tree at the same commit
git stash push -u -m "gate-triage"
<run the failing gate command>
echo "exit=$?"
git stash pop
```

Compare the two runs:

| Clean-tree result | Reading | Action |
|---|---|---|
| Same failures | Pre-existing repo defect | Report it; fix at its source if in scope |
| Passes | Your change caused it | Fix your change |
| Different failures | Mixed | Separate the pre-existing set from yours; fix both or report both |

Record which comparison you ran and its result in the commit or the report.
A claim of "pre-existing, not mine" without this evidence is an assumption.

## Step 3 — decide the escape, and never reach for `--no-verify` first

`--no-verify` is a last resort, never a first move. In order of preference:

1. **Fix it at the source** and commit together (correct when the defect is
   small and in scope).
2. **Fix it in a separate commit**, then commit your own work (correct when the
   two changes are genuinely unrelated — keeps the history honest).
3. **Present the choice to the operator** when the fix is large, out of scope,
   or touches a subsystem the operator owns.
4. **`--no-verify`** only with explicit operator authorization, and say in the
   report that the gate was bypassed and why.

The failure mode this avoids: bypassing a gate because it is inconvenient makes
a real regression invisible, and the report claims a green gate that never ran.

## Step 4 — check whether the flagged files are generated

When a validator emits the *same* error once per file across many files, it is
usually reading a generated tree:

```bash
git check-ignore -v <flagged-path>     # ignored => generated/local
git ls-files <flagged-path>            # empty  => untracked, not committable
```

Then read the declared source of truth and check whether it is already correct.
If the source is right and the generated tree is stale, the defect is that the
tree was never regenerated — not that N files are wrong.

Repair with the generator, not by hand:

```bash
<generator> --check     # dry run first; confirms drift and names the files
<generator> --full-tree # or whatever regenerates the tree
<validator>             # must now pass
```

Hand-editing generated bytes is the wrong repair three times over: it is
overwritten by the next regeneration, it cannot be reviewed as a meaningful
diff, and because the files are gitignored it produces a commit that claims a
fix while containing none of it. If the source of truth is *also* wrong, fix
the source, regenerate, then re-validate — never edit the generated output as
the primary repair.

## Step 5 — verify and report

After any repair, re-run the gate for real and capture the exit status. Report:

- the gate that blocked, and the exact failing check
- the attribution evidence (clean-tree comparison result)
- the repair performed (generator invocation or source fix)
- the post-repair gate result
- whether anything was bypassed, and under what authorization

A gate that blocks, is fixed, and passes is a completed step. A gate that was
bypassed is a disclosed exception — say so rather than reporting a clean run.
